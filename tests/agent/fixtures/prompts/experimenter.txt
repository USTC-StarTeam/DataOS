   "status":"review",
   "stages":{
     "data":  {"rows":<int actually written to data/sft>,
               "requested_rows":<int the recipe asked for>,
               "fingerprint":"<content hash of train.json>"},
     "train": {"model_path":"<the model dir you scored>",

Every stage also accepts, and SHOULD carry when true:
  - `"error"`: what broke in THIS stage — which gate or tool refused, and why. This is also how
    '哪个阶段挂的' gets answered: the stage carrying an error is the one that failed.
  - `"fixes"`: the mechanical workarounds THIS stage needed. Put them on the stage that needed
    them, never in one run-level list: a train-stage `max_steps` added to fit the budget and a
    data-format cast mean completely different things, and a flat list is how a 0.40-epoch node
    was once read as a completed epochs comparison.
  - `"script"`: `{"path":"<abs path>","sha256":"<sha256sum>"}` for a script YOU wrote for that
    stage, or omit it when the tool did all the work. Never `""` — a path with no hash is not
    identification, and the recipe's real identity is the hash.

RULES
- The eval NUMBERS are not yours. Name the DIRECTORY (`summary_dir`) and stop there: after you
  finish, the runtime reads that dir's `summary.json` and fills in `score` / `limit` /
  `n_samples` / `stderr` / `elapsed_s`, plus a `checkpoint_sweep` of every eval dir under this
  node when you scored more than one. Which measurement the node stands behind is your DECISION —
  you may have scored six checkpoints — but what each one measured is the harness's to say, and
  it already said it. Score every checkpoint you want: they all reach the leader whether or not
  they won, which is the point.
- `requested_rows` vs `rows`: a selector with `strict=false` silently returns whatever the pool
  had. If they differ by more than 10%, say so in the data stage's `fixes`.
- On a BASELINE run there is no data and no training: omit both stages and start the cursor at
  `eval`. A stage that does not apply is absent, not empty.
- Extra fields are welcome. If you learned something the shape above has no slot for — where the
  parser lives, what target format it wants, what your pre-check found — add it. The leader sees
  everything in this file.

ADVANCE THE CURSOR AS YOU GO — the file on disk is how the runtime knows you are alive and where:
  1. starting          -> `{"id":...,"status":"data"}`
  2. data written      -> add `stages.data`, set `status` to `"train"`
  3. training finished -> add `stages.train`, set `status` to `"eval"`
  4. eval scored       -> add `stages.eval.summary_dir`, set `status` to `"review"`
  5. review written    -> add `stages.review`, set `status` to `"completed"`
If a stage breaks and you cannot get past it, put the cause in that stage's `error` and set
`status` to `"failed"`. `failed` is the ONLY failure value: a Slurm TIMEOUT, a CUDA OOM, a budget
that ran out are all `"failed"` plus the reason in `error`.

the cursor where it is. It is already true, and it already says you are not finished.
