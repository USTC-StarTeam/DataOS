## 批次 1 — 预算会计（✅ 已修，2026-08-08）

三个问题同源于 `_queue_wait_s`（subagent_executor.py:124-153）：

1. **P0：排队抵扣可被永久击穿**。被 cancel 时仍在 PENDING 的 job，sacct 的 Start 列是
   `None`（非代码假设的 `Unknown`/空）→ shell 里 `date -d "None"` 失败 → 用 `$now` 封顶 →
   该 job 贡献的"排队时长"随时间无限增长 → `budget.py:47` 的 elapsed 被冻结 → 10h 预算
   停止永不触发；`_run_one` 的 experimenter timeout 同理被无限延长。集群实证：07-01 以来
   318 个此类 job。触发路径是自愈常规动作（cancel+重提）。
2. **resume 重复抵扣**：budget 语义是 per-invocation 墙钟，但 credit 扫
   `runs_base/<project_id>` 下全部历史 job（无 Submit 下界）——每次 `--resume` 把之前的
   排队总量再送一遍，预算被动膨胀。
3. **eval 排队不可见**：发现口径是 `slurm-*.out`（job 开跑才存在）+ `-name 'handle.json'`
   （只匹配 dataos-train）；dataos-eval 的 `eval_handle.json` 不匹配 → eval job PENDING
   期间零抵扣，预算照烧、experimenter deadline 照缩——排队豁免设计的反面。

**修复**：sacct 改取 `Submit,Start,End`（加 `-X` 滤步记录），epoch 在集群侧解析后 Python
算重叠：终态未启动用 End 封顶（真机验证：被取消 job 封顶在取消时刻）、仍在排队用 now、
credit 取与本次 invocation 起点的重叠区间（`set_invocation_wall_start` 在 run_auto 入口
锚定）；handle 发现放宽为 `*handle.json`。单测 `_queue_credit_s` 六例钉死。

## 批次 9 — 配置根隔离撤回（✅ 已撤，2026-08-10）

批次 6 引入的"每角色一个私有配置根"（`CODEX_HOME`/`CLAUDE_CONFIG_DIR`/`KIMI_CODE_HOME`/`QWEN_HOME`
指向 `~/.cache/dataos-agent/<pid>/<role>/home`）**已整体移除**。它与这几个 CLI 的认证方式不兼容，
而且不可能在包内解决：

1. **OAuth 凭据住在配置根里，且 refresh token 是一次性轮换的。** N 个进程各持一份副本，第一个刷新
   成功就让其余全部失效。7 个 run 并发时每个 run 3 个角色 → 最多 21 份同一个一次性 token。
2. **换成 symlink 也不是解法**：配置根其余部分看起来是空的时候，CLI 可能**重新初始化**凭据存储而不是
   刷新，写入会穿过链接落到真实文件上 —— kimi 在批次 8 的实现过程中就这么把一个有效登录清零了。

保留的隔离是唯一与凭据无耦合的那一半：**run 的 cwd 是仓库外的私有目录**
（`llm.config.role_cwd`，原 `role_dirs`），这正是让 CLI 无法自动发现仓库内开发期 AGENTS.md 的机制。
`~/.codex` / `~/.claude` 里的全局内容现在**有意与宿主共享** —— 这台机器上 `~/.codex/AGENTS.md`、
`~/.claude/CLAUDE.md` 都不存在、`config.toml` 只有 trust_level，所以实际污染为零。
**不要在没有解决凭据问题之前重新加回搬迁。** 理由写在 `dataos_agent/_home.py` 的模块 docstring 里。

附：2026-08-10 起 7 个 4b2 v5 run 时全部立刻失败于
`Failed to refresh token: your refresh token was already used`。**该失效先于本次启动**（7 份副本与

### 10.1 训练栈：32 次 OOM，全部自伤（P0）

现场显存构成（`grep -r torch.OutOfMemoryError`，去重后）：

    申请 2.32 GiB | 空闲 2.24 | 本进程占 76.93   ×4      申请 6.66 | 空闲 5.30 | 本进程占 73.87  ×4
    申请 7.30 GiB | 空闲 5.27 | 本进程占 73.90   ×3      申请 2.32 | 空闲 0.95 | 本进程占 78.22  ×3

每次训练进程自己占 79.18 GiB 里的 62–78 GiB，**没有别的租户**——曾怀疑是 vLLM 评估服务同卡
抢显存（`start_vllm_server` 确实不传 `--gpu-memory-utilization`、走 vLLM 默认 0.9，而 direct
路径有 `DIRECT_GPU_MEMORY = {humaneval: 0.3, gpqamain: 0.8}`），**显存数字已排除该假设**；那条
仅作为潜在风险另记（10.6）。

真因精确：**2.32 GiB = 4096 × 151936 × 4 bytes**，正是 `transformers/loss/loss_utils.py:36
fixed_cross_entropy` 里 logits 的 fp32 上采样。栈顶固定为
`modeling_qwen3.py:750 forward → loss_utils.py:64 ForCausalLMLoss → :36 → F.cross_entropy`。

**触发条件是每微批 token 数（= `cutoff_len × per_device_train_batch_size`），32 个 full-SFT
节点分得干干净净**：

| 每微批 token | packing | 节点数 | OOM 作业 |
|---|---|---|---|
| 2048 | true / 未设 | 12 | **0** |
| 4096 | **true** | **8**（全是 arena） | **24**（8/8 节点全中） |
| 4096 | false / 未设 | 12 | 8（3/12 节点中：aime r002、gsm8k r002/r005） |

2048 是安全线，4096 是悬崖。`packing: true` 让每一步恒为满 4096 稠密 token，把悬崖从"偶尔
撞上"变成"必然"——8/8 全中；不 packing 时批长随数据分布起伏，只有偶发的长批越界（gsm8k
r003/r004/r006 同配置 0 次，r002/r005 分别 3 次和 1 次）。

train_config 里能开的都已开满（`gradient_checkpointing: true` / `flash_attn: fa2` /
`optim: adafactor` 或 `adamw_torch_fused` / `per_device_train_batch_size: 1` / `bf16`），
**agent 无处可降，只能盲目重试**——arena round 1/5/8 的 train_config 逐字节相同即证据。
优化器不是判别变量：arena r0008（默认 AdamW）OOM 5 次、r0005（adafactor）OOM 4 次。

代价：arena 7 个节点提交 38 次作业（正常 14 次），单节点最高 8 次
（round-0001/full-sft-writingprompts-20k）；aime round-0002 提交 4 次，gsm8k round-0002 提交 3 次。

修：① LLaMA-Factory `enable_liger_kernel: true`（model_args.py:136；分块交叉熵，fp32 logits
不再整块落地，直接消掉该峰值）——**注意当前 dataos_sft venv 未安装 liger-kernel 包，需先装**，
未采纳；② **✅ 已修 2026-08-10**：`launchers/base.py::build_preamble` 加 `_ENV_DEFAULTS`，
所有训练作业默认 `export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`，可被 `job.env`
覆盖。此前 43 个 run_train.sh 里只有 4 个碰巧带这行（agent 自己临时加的），现在覆盖全部；
③ 未采纳：把 `cutoff_len × batch` 钳到 2048，或长目标 bench 强制 `packing: false`。

⚠️ 只做了 ②：碎片整理能救回"同配置有时过有时不过"的那部分，但**悬崖本身还在**——4096
token 的峰值分配没有消失，只是更不容易因碎片而失败。要根除仍需 ① 或 ③。

### 10.4 dataos_operator 合约缺陷（✅ 已修，2026-08-10，operator 0.8.1）

    dataos_operator/core/contracts.py:539, in transform
    TypeError: MapperOperator expected a record or dataset,
               got <class 'datasets.arrow_dataset.Dataset'>

真因在 `is_dataset`（contracts.py:100-105）：

    if not isinstance(value, Sequence):
        return False

HuggingFace 的 `datasets.Dataset` 能 `len()`、能索引出 Mapping、能迭代出 records，**但没有注册
成 `collections.abc.Sequence`** —— 于是这个 isinstance 判断把工具箱最自然的输入（刚加载的数据源）
一律拒掉，报的还是"expected a record or dataset"这种看着像调用方写错的信息。

修（`tools/operator/` 已迁入本仓，可直接改源码；**0.8.0 → 0.8.1**）：`is_dataset` 在非 Sequence
分支改为鸭子类型判断 —— 有 `__len__` + `__getitem__` 且第 0 行是 Mapping 即算 dataset。只看第 0 行
而不是像 Sequence 分支那样 `all(...)` 全扫，因为索引 Arrow 表会物化行、全扫等于解码整张表。
不 import `datasets`：工具箱不该依赖它。回归测试 `tools/operator/tests/test_contracts.py` 两条：
真 HF Dataset 能过（并断言它确实不是 `Sequence`）、`__len__`+`__getitem__` 但元素非 Mapping 的对象
（如数字数组）不能被误判。

配套（提示侧）：`experimenter/context/operator_use.yaml` 仍加了一条写明 `dataos_operator.Dataset`
的包装姿势 —— 43 份 build_data.py 里 27 份本来就这么写，现在两条路都通。

⚠️ 部署：改完需 bump 版本 + 改 `env.yaml` 两处 `dataos_tools` 声明（PTB_H100_slurm 与
PTB_H100_slurm_normal 指向同一个物理 venv）+ 在集群跑 `scripts/sync_envs.py`。

### 10.9 AUTO(-2)：自伤条款让子集成为严格劣势选项（P1，接批次 2/7）
