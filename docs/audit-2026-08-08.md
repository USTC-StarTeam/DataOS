## 批次 1 — 预算会计（✅ 已修，2026-08-08）

三个问题同源于 `_queue_wait_s`（subagent_executor.py:124-153）：

1. **P0：排队抵扣可被永久击穿**。被 cancel 时仍在 PENDING 的 job，sacct 的 Start 列是
   `None`（非代码假设的 `Unknown`/空）→ shell 里 `date -d "None"` 失败 → 用 `$now` 封顶 →
   该 job 贡献的"排队时长"随时间无限增长 → `budget.py:47` 的 elapsed 被冻结 → 10h 预算
   停止永不触发；`_run_one` 的 experimenter timeout 同理被无限延长。集群实证：07-01 以来
   318 个此类 job。触发路径是自愈常规动作（cancel+重提）。
2. **resume 重复抵扣**：budget 语义是 per-invocation 墙钟，但 credit 扫
   `runs_base/<project_id>` 下全部历史 job（无 Submit 下界）——每次 `--resume` 把之前的
   排队总量再送一遍，预算被动膨胀。
3. **eval 排队不可见**：发现口径是 `slurm-*.out`（job 开跑才存在）+ `-name 'handle.json'`
   （只匹配 dataos-train）；dataos-eval 的 `eval_handle.json` 不匹配 → eval job PENDING
   期间零抵扣，预算照烧、experimenter deadline 照缩——排队豁免设计的反面。

**修复**：sacct 改取 `Submit,Start,End`（加 `-X` 滤步记录），epoch 在集群侧解析后 Python
算重叠：终态未启动用 End 封顶（真机验证：被取消 job 封顶在取消时刻）、仍在排队用 now、
credit 取与本次 invocation 起点的重叠区间（`set_invocation_wall_start` 在 run_auto 入口
锚定）；handle 发现放宽为 `*handle.json`。单测 `_queue_credit_s` 六例钉死。

## 批次 9 — 配置根隔离撤回（✅ 已撤，2026-08-10）

批次 6 引入的"每角色一个私有配置根"（`CODEX_HOME`/`CLAUDE_CONFIG_DIR`/`KIMI_CODE_HOME`/`QWEN_HOME`
指向 `~/.cache/dataos-agent/<pid>/<role>/home`）**已整体移除**。它与这几个 CLI 的认证方式不兼容，
而且不可能在包内解决：

1. **OAuth 凭据住在配置根里，且 refresh token 是一次性轮换的。** N 个进程各持一份副本，第一个刷新
   成功就让其余全部失效。7 个 run 并发时每个 run 3 个角色 → 最多 21 份同一个一次性 token。
2. **换成 symlink 也不是解法**：配置根其余部分看起来是空的时候，CLI 可能**重新初始化**凭据存储而不是
   刷新，写入会穿过链接落到真实文件上 —— kimi 在批次 8 的实现过程中就这么把一个有效登录清零了。

保留的隔离是唯一与凭据无耦合的那一半：**run 的 cwd 是仓库外的私有目录**
（`llm.config.role_cwd`，原 `role_dirs`），这正是让 CLI 无法自动发现仓库内开发期 AGENTS.md 的机制。
`~/.codex` / `~/.claude` 里的全局内容现在**有意与宿主共享** —— 这台机器上 `~/.codex/AGENTS.md`、
`~/.claude/CLAUDE.md` 都不存在、`config.toml` 只有 trust_level，所以实际污染为零。
**不要在没有解决凭据问题之前重新加回搬迁。** 理由写在 `dataos_agent/_home.py` 的模块 docstring 里。

`Failed to refresh token: your refresh token was already used`。**该失效先于本次启动**（7 份副本与

### 10.1 训练栈：32 次 OOM，全部自伤（P0）

真因精确：**2.32 GiB = 4096 × 151936 × 4 bytes**，正是 `transformers/loss/loss_utils.py:36

| 每微批 token | packing | 节点数 | OOM 作业 |
|---|---|---|---|

r003/r004/r006 同配置 0 次，r002/r005 分别 3 次和 1 次）。

### 10.4 dataos_operator 合约缺陷（✅ 已修，2026-08-10，operator 0.8.1）

    dataos_operator/core/contracts.py:539, in transform
    TypeError: MapperOperator expected a record or dataset,
               got <class 'datasets.arrow_dataset.Dataset'>

真因在 `is_dataset`（contracts.py:100-105）：

    if not isinstance(value, Sequence):

而不是像 Sequence 分支那样 `all(...)` 全扫，因为索引 Arrow 表会物化行、全扫等于解码整张表。
不 import `datasets`：工具箱不该依赖它。回归测试 `tools/operator/tests/test_contracts.py` 两条：
真 HF Dataset 能过（并断言它确实不是 `Sequence`）、`__len__`+`__getitem__` 但元素非 Mapping 的对象
（如数字数组）不能被误判。

2. **权重空间插值 / 任务向量缩放**。其交付模型 `candidate7_late_a0375` =
   `0.375×candidate4_midpoint + 0.625×candidate4_final`，并做了完整系数扫描（含 **负系数外推**）：

   | midpoint 权重 | 0.375 | 0.250 | 0.125 | −0.125 | −0.250 | −0.500 |
   |---|---|---|---|---|---|---|
   | 全量分 | **81.12** | 80.59 | 80.21 | 80.29 | 80.97 | 80.74 |

我们的 leader **已正确识别问题是"更新幅度"**，然后用**缩数据**去逼近"缩小更新"：
60k full(23.58) → 30k full(16.00) → 20k lora(63.31) → 5k lora(68.01) → 1500 lora(69.75) →
800 lora(68.31)。误差从 −56.71 单调收敛到 −0.15 后**在 800 条处反转**——代理轴在小端失效，
因为缩数据同时改变了数据分布和更新幅度，无法解耦，且其极限是"不训练"而非 α≈0.375 那个点。

修：新增一种**非训练实验类型** `merge`，参数 (父节点A, 父节点B, α)，只做权重插值 + 评估。
成本仅一次评估（~15 min），却打开一条连续搜索轴。同时让 `train` 支持 `save_strategy: steps`
并允许 plan 指定"以哪个 checkpoint 为父节点"。**对所有"baseline 已高"的 bench 都适用，而这
类 bench 在现有动作空间里几乎必然打不动。**

**进展（2026-08-11，dataos-train 0.1.5）：第 1 步已落地——checkpoint 现在存得下来。**

`SFT.save_steps` / `save_total_limit` 成为**有类型的字段**（此前只能走 `method.extra` 后门，没人知道，
而且走后门的话 dataos-train 自己看不见它）。渲染时强制 `save_only_model: True`：优化器状态约是权重的
4 倍（fp32 master + Adam m,v），而我们**从不 resume**——这里的 checkpoint 存在的意义是被**评估**、
以及作为新一轮的起点，两者都只要权重。SmolLM3-3B 一个 checkpoint 因此从约 40 GiB 降到约 5.7 GiB。

`cli.precheck_disk` 的因子随之从固定 1.5 变成 `1.5 + save_total_limit`（仅 full/freeze；LoRA 的
checkpoint 是 adapter，不计入）——这正好兑现了 12.11 里"这是下界，保留 checkpoint 会成倍放大"那句话。

同时给 `_SFT_FIELDS` 补了漂移测试。它决定 plan 的键进**有类型字段**还是 `method.extra`：两者都能到
LLaMA-Factory，但只有前者对 dataos-train 自己可见——一个存 checkpoint 的 plan 若落进 `extra`，
磁盘预检就会放行一个装不下的 run。这个镜像此前**没有任何测试守着**。

**剩下三步（未做）**：② 报告带回 `checkpoints` 列表，leader 才看得见；③ 让 checkpoint 成为**可独立
评估的节点**（否则 midpoint 的分永远混在子节点里，而"midpoint 强过 final"这个发现本身就必须靠单独
评估才能得到）；④ 告诉 leader 这一招，包括**扫 n 个 checkpoint 时先用子集定位峰值区间、只对峰值点做
全量评估**——这也是 AUTO(-2) 子集评估第一个真正的用武场景（对照批次 2/7/10.9：两批 100 个节点零使用）。

**prompt 必须等 ②③ 打通再加**：只做了"存"就告诉 leader，它会存一堆没法用的 checkpoint。

补一条为什么这条轴值得投入：134 条实验记录里约 20 条是**纯数据量扫描**（6k→12k→24k、top-4k/6k/8k/12k、
pool 20k→40k、xlam 5k→15k→28k…），绝大多数结论是 flat/no-scale。一次扫描要 3 次训练；
checkpoint 扫描只要 **1 次训练 + 每点一次评估**。但两者**不等价**：默认 `lr_scheduler_type` 是 linear
（`config.py` 未设，落到 HF 默认），所以 24k 跑到一半的 checkpoint 学习率还在峰值的 50%、没退火，而
12k 跑完的 final 已退到 ≈0；再加上 epoch 数不同（记录：bfcl 15k×1ep=66 vs 5k×3ep=92）。
**checkpoint 测的是"在一条轨迹上走多远"，不是数据量的替代品**——但那恰好就是 11.1 里 leader
识别对了、却只能拿缩数据当代理去逼近的那条轴。

### 11.2 P0 — 两个 deadline 口径不一致 → 77 个僵尸轮（✅ 已修，2026-08-11）

`fan_out`（subagent_executor.py:655-661）在预算耗尽时跳过实验、写一份
`status: failed, error: "skipped: wall-clock budget exhausted"` 的报告然后 `continue`；主循环
拿到它照常进入 review，**让 reviewer 去评论一个从未运行的实验**，再进入下一轮 planning。

    轮次去向（153 轮）：有分 66 · 有 plan 但无实验目录 77 · 实验无分 10
    "budget spent" 计数：gsm8k 36 · healthbench 28 · aime2025 12（= 76，与 77 吻合）

每个僵尸轮的成本 = 一次 leader planning（context bundle ~25K 字符）+ 一次 review 调用，全是
纯浪费；reviewer 的产出还污染 `recent_reviews`——连续几十条 "The prediction cannot be
evaluated … no recorded execution … no 439-example probe score"，把真正有信息的历史挤出窗口。
这也解释了 gsm8k 的 round 计数冲到 50 而有分节点只有 15（批次 5 记的"invalid-plan 跳轮不留痕"
在此升级为 P0：不是留痕问题，是不终止问题）。

另注：僵尸 plan 里 `eval_limit=439`（gsm8k 的 probe floor）——**AUTO 终于被用了**，恰好是在预算
见底、leader 开始缩一切的时候；同批还出现 `sample_size=1` 的 plan。与 v4 的
`eval_limit=1` 是同一种末期退化，只是这次它们一个都没运行。所以"本批子集使用 0"的准确说法是
"0 个跑成的子集节点 + 76 个从未运行的子集 plan"。

**根因不是"循环没有终止检查"**——`while True` 开头一直有 `_budget.stop_reason`。真因是同一个预算
被算了两遍、规则不同：

    loop.py:589-591  credit = _queue_wait_s(cfg);  stop_reason(..., queue_credit_s=credit)
    budget.py:47     elapsed = now - started - credit        ← 减了排队时间
    loop.py:750      deadline = started + max_wall_clock_s   ← 没减

于是 run 必然进入一个稳定态：真实墙钟已过 `started+budget`（`fan_out` 拒绝启动任何实验），
而扣掉 credit 的 elapsed 仍未到（`stop_reason` 返回 None，循环继续）。窗口宽度 = 累计排队时间,
所以排队最久的三个 run 僵尸轮最多（36/28/12），排队少的四个为 0。第三处 `_remaining_hours`
（leader 读到的余量）也自己算一遍且无帽，所以 leader 以为还能塞小实验——`eval_limit=439`、
`sample_size=1` 都出自这里。

**排队豁免（批次 1）本身是对的**，错在只用于放宽停止条件、没同步放宽实验 deadline。

修（✅ 2026-08-11）：`budget.credited_deadline()` 成为**唯一**口径，三处调用它
（`stop_reason` / `fan_out` deadline / `_remaining_hours`），并给豁免加硬帽
`_MAX_CREDIT_FRACTION = 0.5`——否则拥塞集群能把 10h 跑成无限（本批 gsm8k 已 11.5h）。
测试：credit 生效 / credit 超帽被夹 / 无 credit / 无预算；并更新
`test_budget_ideal_time_excludes_queue_credit` 以钉住加帽后的语义。

### 11.3 P0 — `template` 默认值写死为 `qwen3`（✅ 已修，2026-08-11，dataos-train 0.1.2）

`spec.py:78,98`：`template: str = "qwen3"`。而 **68/68 个 plan 里 leader 从未写过 `template`**，

后果：Qwen3 名副其实；**SmolLM3 碰巧对**（同为 `<|im_start|>/<|im_end|>`，`replace_eos=True`

测试 6 条：三族映射、续训场景（断言路径里查不到族名）、未知族抛错、目录读不到抛错、

## 批次 12 — 训推模板同构 / 协议权威（2026-08-11，随 `fcd5a10` 落地）

起因是批次 11.3（`template` 写死 `qwen3`）修完后的一个追问："既然训练和推理都用官方模板，
为什么还会不一致？"——前提不成立，而顺着查下去翻出了下面这些。**本批的判据是同一句话：
run 钉死的东西，agent 和工具都不该能改；而"协议"必须是一处声明，不是产物的属性。**

### 12.1 P0 — 训练模板与评估模板从未被任何代码比对过（✅ 已修 + 已装闸）

训练走 LF 的**槽位**模板（4 个格式串），评估走官方 **jinja 程序**（`smollm.jinja` 5942 字节，
含 reasoning mode 分支、`/system_override`、tools、日期注入）。两者是同一个格式的两种表示法，
而"它们一致"这件事，**唯一的保证是有人肉眼比对过两个文件**。

实测差距（同一条 user 消息、数据行无 system）：

| | 字节 | 内容 |
|---|---|---|
| 训练侧（LF `smollm3`，`default_system=""`） | **55** | `<\|im_start\|>user\n…<\|im_start\|>assistant\n` |
| 评估侧（`smollm.jinja`，评估侧真实参数） | **1360** | 完整 system 头 |

`smollm.jinja` **总是**发一个 system 轮，且 `enable_thinking` 默认为真，于是注入
`## Metadata`（含当天日期）+ 一段"以 `<think> Thought </think> Solution` 作答"的长指令。
**smol3 那批 7 个 bench 的每个节点，都是在没见过这条指令的情况下被它评分的。**

而训练侧当时**也补不上**：SFT 的 `dataset_info.json` 没有 `columns` 映射，LF 会丢掉数据行的
`system` 字段（这是已知问题，见 memory `dataos-train-drops-system-column`）。

修：
1. 把 `smollm.jinja` 的 system 头**手工翻译**进 LF 注册（`/think` 与 `/no_think` 各一份，
   逐字节）。唯一对不上的是 `Today Date`——jinja 在评估时渲染、dataos-train 在训练开始时渲染，
   同一天相同、跨天差一行。
2. **装闸**：`tools/train/tests/test_train_eval_template_parity.py` 把同一组 messages 分别过
   jinja 和 LF 槽位，不一致就失败。jinja 侧只需一个 `{% generation %}` no-op 扩展（该标记是
   给 `return_assistant_tokens_mask` 用的，对渲染无贡献），**不需要 transformers、不需要
   tokenizer**，所以我们手写的那一族在任何机器上都被守着；LF 内建的两族需要 llamafactory。

闸门第一次运行就抓到一处：`smollm.jinja` 的 `/no_think` 分支会在生成提示后预填
`<think>\n\n</think>\n`，而 LF 自己的 `qwen3_nothink` **不建模这个预填**。jinja 是协议，
所以改的是我们这边。在集群 sft_env 实跑：gemma3 / qwen3 / smollm3 / LF-free header **4/4 通过**。

**qwen3 与 gemma3 本来就是一致的**——排查中一度误判它们也偏，原因是渲染时传了
`enable_thinking=False`，而评估侧从不传这个参数。

### 12.2 P0 — 评估模板曾让位于模型目录里的产物（✅ 已修）

`protocol_tokenizer` 原本是 `if tok.chat_template: return None`——模型自带模板优先于协议模板。
而模型目录里那份**永远不是被声明的那份**，取决于基座是哪一个：

| 基座 | `final_model/chat_template.jinja` 的来源 | 实测 |
|---|---|---|
| Qwen3-4B-Base（自带模板） | `save_pretrained` 原样带出**基座那份**，LF 不覆盖（`fix_jinja_template` 只在 tokenizer 无模板时写） | 4116 字节，与基座逐字节相同 |
| SmolLM3-3B-Base（不带） | LF 用 `_get_jinja_template()` 从槽位**反推**一份 | 一个 bfcl 节点 **559 字节，全文没有 "tools" 二字**（协议模板 5942 字节、18 处 tools） |

反推是结构性残缺的：`_get_jinja_template` 只重建 system/user/assistant 三个角色和一个 for 循环，
**丢掉 tools 分支、reasoning 分支、Metadata**。一个纯工具调用的 bench，在一份连 tools 都渲染不出
的模板下打分。

它没在 smol3 那批炸掉，只因 bfcl 走 **server 路径**（`vllm serve --chat-template` 显式传协议模板），
那 559 字节只影响 **direct 路径**的 humaneval / gpqamain。也就是说：**同一个 run 里五个 bench 用
5942 字节的协议模板，两个 bench 用 559 字节的残片，两批次无人察觉。**

一个此前写错的因果需要订正：这**与 transformers 版本无关**。4.52.3 一样会写
`chat_template.jinja`（Qwen v5 批次就是在 4.52.3 下训的，文件在）。所以 12.2 不是 11.4 升级的
副作用，是一个独立的既有缺陷。

修：协议**无条件**赢。`summary.json` 的 `runner` 段改记 `displaced_model_template`——
"带了一份**与协议不同**的模板"才为真；"带了一份"几乎恒真、等于没信息。

对 Qwen 的影响实测为 **零**：基座那份与 `qwen3.jinja` 差 41 行，但全是防御性写法
（`message.content is string` 之类），在纯文本单轮 / 带 system / 带 tools 三种形状下
**渲染逐字节相同**（86 / 101 / 563 字节）。

### 12.3 P1 — 训练 env 现在由配置按模型族决定（✅ 已修，dataos-train 0.1.3）

11.4 的直接修法是把 `dataos_sft` 的 transformers 往上抬，但"哪个 env 能训哪个架构"是**依赖事实**，
不是 spec 能断言的东西——下一个新模型族会重演同一条路。

机制照 LF 后端已有的 PPO env domain（`llamafactory:ppo`，因 TRL pin 冲突而独立）复用，多加一个
族维度：

| 层 | 职责 |
|---|---|
| `env.yaml` 的 `tools.*.model_families` | **唯一权威**：这个 env 的 transformers 认识哪些 `model_type` |
| `src/dataos/agent/train_spec.py` | 机械展开成 `llamafactory@<family>` 域；brain 不认识"族"是什么 |
| `spec.py::env_for(backend, method, family)` | 最具体优先：`b:m@f` → `b:m` → `b@f` → `b` |
| LF 后端 | 读模型**自己的** `config.json` 的 `model_type`，同一次读同时决定模板和 env |

关键取舍：**声明里没有的族在 build 时硬报错，不回落到未限定域**——回落正是 11.4 那 146 个废作业的
形状。报错文案直接给出要编辑的那一行。加新模型族因此是一次配置编辑，不是一次代码改动。

（brain 主机看不到 `/data`，读不了模型的 `config.json`，所以族名只能在集群侧解析——正好是
`resolve_template` 已经在做的那一步。）

### 12.10 P0 — bfcl 的 per-doc `tools` 上错了车，两批分数作废（✅ 已修，2026-08-11）

`construct_requests` 把**每道题不同**的 `tools` 放进了 `gen_kwargs`，而 `gen_kwargs` 是**整批共用**的。
lm-eval 三层叠加把它变成静默错误：

1. 请求按 gen_kwargs 分组，键构造用 `tuple(value) if isinstance(value, Iterable)`——`tools` 是
   `list[dict]`，转出来仍不可哈希 → `TypeError`；兜底是 `res[tuple(fn(ob))]`，而 `tuple(字典)`
   **只取键名**，值被整个丢弃 → 全部题挤进同一组。
2. `num_concurrent > 1` 时切块参数 `n=0` → 整组就是一个批次。
3. 批次用 `gen_kwargs=copy.deepcopy(all_gen_kwargs[0])` 发送。

于是第 2..N 道题被要求调用**第 1 道题的函数**。实证（新写的测试在旧代码上的输出）：

```
doc 'beta' was sent tools ['alpha']
```

代价：两批 ×bfcl 的全部分数都是在测 harness，不是在测模型。

| run | baseline | 全部节点 |
|---|---|---|
| smol3 bfcl（15 节点） | 0.0 | 0.0–7.0 |
| 4b2 v5 bfcl（8 节点） | 4.0 | 2.0–16.0 |

两批的 eval 命令里 `--num-concurrent` **一次都没出现**（全吃脚本默认 32）；同一 bench 用并发 1 的
手工 Qwen3-**1.7B** 系列到过 60–92。**这 23 个节点的 bfcl 分数不可作为基线引用。**

修：`tools` 改为随**上下文**走（上下文是逐请求传递的，`gen_kwargs` 才是共用的）——
`_chat_instance(..., request_fields={"tools": ...})` 把它编进 `JsonChatStr`，
`DataOSLocalToolChatCompletion._create_payload` 再把 `messages` 以外的键并回请求体。

选这个修法而不是"把并发降到 1"，是因为后者要付 10–20 倍墙钟（bfcl 111s → 20~35 分钟，而
gsm8k 会从 536s 变成约 4 小时，全局不可行）。也不能选"把 tools 序列化成字符串让哈希成功"：那会
变成每题一组，而上游是 `for chunk in chunked: asyncio.run(...)` **逐组串行**，等于又退回并发 1。
tools 一旦离开 gen_kwargs，各题 gen_kwargs 完全相同 → 干净地落进一组 → 并发跑满，
而每条带自己的 messages。**并发数在这里从来不是性能旋钮，是正确性开关；修好之后它才真正只是性能旋钮。**

闸门：`tests/tasks/test_bfcl_per_doc_tools.py`（4 条，需 lm-eval/aiohttp/tenacity，在 eval_env 里跑）。
新旧两版对照验证过：旧代码在第 1、2 条上红，新代码 4 条全绿。第 3 条专门守着"其他五个 bench 的
请求字节不变"，所以它们的 baseline 不受影响。

### 12.11 P1 — 训练提交前不检查磁盘（✅ 已修，2026-08-11，dataos-train 0.1.4；接批次 10.5）

4b2 v5 那批把 `/data2` 写满，训练**跑完之后**死在 `save_pretrained`：GPU 小时花掉了，什么都没拿回来。
而且报错本身有误导性——文件系统满在 safetensors 那里表现为 "File too large (os error 27)"，
读起来像尺寸 bug 而不是空间问题，于是排查成本付了两次。

修：`dataos_train.cli.precheck_disk(spec)`——按基座模型权重文件的大小 × 1.5 估算这一轮要写回的量，
和 `run_dir` 所在文件系统的可用空间比；不够就在**提交前**拒绝，并把"现有多少 / 需要多少"打出来。
`run_dir` 此时尚未创建，所以向上找到第一个存在的祖先目录再探测。基座路径不可读时（例如在看不到
模型的机器上构建 spec）不报错——没有可比的量，拒绝反而会误伤。

三条边界写在代码里而不是靠人记：这是**下界**不是保证（保留 checkpoint 会成倍放大），它**不预留**
空间（同一文件系统上另一个作业可以在这之后把它填满），因子 1.5 覆盖的是"全参写回一份 final_model"
加上 LoRA 的合并导出。

顺带修掉一处不一致：`submit` 此前**完全不走** `validate()`——直接把 TrainSpec 交给 `submit` 时，
后端会拒绝的 spec 照样被提交。现在 `build` / `submit` / `validate` 三条路走同一个漏斗
（`_build_or_die`），所以 `validate` 报 ok 的 spec 不可能被 build 拒绝。
